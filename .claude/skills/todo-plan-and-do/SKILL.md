## 依頼内容
$ARGUMENTS

## 最新のTODOファイル（最大5件）
!`ls todo/ | tail -5`

## 手順
計画（フェーズ1）を立てて TODO ファイルを作成したら、確認を挟まずそのまま実装（フェーズ2）に進む。

### フェーズ1: 計画
0. 依頼内容が既存の TODO ファイルのパス（例: `todo/077-todo.md`）なら、Read で読んでその内容を依頼内容として扱う。以降「上書きモード」とする
1. 依頼内容を理解し、関連するコードを Glob / Grep / Read で調査する
2. 仕様・方針・範囲などで不明点や判断が分かれる点があれば、AskUserQuestion で質問して回答を待つ（推測で進めない）
   - 依頼文から読み取れない仕様（挙動・出力形式・対象範囲・エッジケースなど）も聞く
   - ただし、答えによって実装が変わる点だけに絞る
3. 回答を踏まえて実装計画を立てる
4. 上書きモードなら番号は決めず、指定されたファイルをそのまま対象にする。それ以外は既存ファイルの最大番号に +1 した番号を3桁ゼロ埋めで決める（ファイルがなければ 001）
5. 上書きモードなら指定ファイルを上書きする（完了済み `[x]` の項目は残す）。それ以外は `todo/NNN-todo.md` を新規作成する（例: 既存が 002 までなら `todo/003-todo.md`）

### フェーズ2: 実装
6. フェーズ1で作成（上書き）した TODO ファイルを対象に、「実装計画」のステップを上から順に実装し、完了するごとに `- [ ]` を `- [x]` に更新する（既にチェック済みのステップはやり直さない）
7. 「テスト・確認方法」を実施し、完了した項目を `- [x]` に更新する

## TODOファイルの形式
# <タイトル>

## 概要
何を・なぜ実装するか

## 調査結果
関連ファイルと現状の構成

## 実装計画
- [ ] ステップ1: 具体的な作業内容（対象ファイル）
- [ ] ステップ2: ...

## テスト・確認方法
- [ ] ...

## 決定事項
質問への回答で決まったこと

## 懸念点・未決事項
- ...

## ルール
- 質問は調査後にまとめて行い、コードを読めば分かることは聞かないこと
- 計画にない作業はしない。必要だと分かった場合は、TODOファイルの「懸念点・未決事項」に追記して報告する
- 計画どおりに進められない場合（前提が違った、別の方法が必要など）は、勝手に方針を変えず、AskUserQuestion で確認する
- 質問への回答で決まったことは「決定事項」に追記する
- テストが失敗した場合、テストを弱めたり無効にしたりして通さない

## 報告
- TODOファイルのパスと計画の要約
- 完了したステップ／全ステップ数
- テスト・確認の結果
- 計画から変わった点、追記した懸念点（なければ「なし」）
